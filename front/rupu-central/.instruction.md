# Instrucciones Frontend - Rupu Central

## Business Token

### Regla Fundamental
**Todas las peticiones HTTP deben originarse desde server actions (`'use server'`), NO directamente desde componentes client-side.** El token se pasa como parámetro a las server actions, nunca se usa `localStorage` directamente en los repositorios.

### Lógica del Business Token

El business token se obtiene y gestiona de la siguiente manera:

1. **Obtener el token existente**: Primero se verifica si ya existe un business token en `TokenStorage` y si el `activeBusiness` coincide
2. **Generar nuevo token**: Si no existe o no coincide, se genera uno nuevo usando el session token
3. **Manejo de Super Admin**: 
   - **IMPORTANTE**: El super admin **SIEMPRE** usa `business_id = 0` en el token, esto NO cambia
   - Cuando el super admin está trabajando en un negocio específico (p. ej., `/properties/16/parking`), el `business_id` del contexto (16) se envía como **query param** en las peticiones HTTP
   - El backend detecta si es super admin (por `business_id = 0` en el token) y lee el `business_id` del query param si se envía
   - Si NO es super admin, el backend siempre usa el `business_id` del token

### Patrón de Implementación

En componentes client-side que necesitan hacer peticiones HTTP:

```typescript
import { useCallback } from 'react';
import { TokenStorage } from '@shared/config';
import { generateBusinessTokenAction } from '@/services/auth/login/infrastructure/actions';

const getBusinessToken = useCallback(async (): Promise<string> => {
  const user = TokenStorage.getUser();
  const isSuperAdmin = user?.is_super_admin || false;
  
  // Super admin siempre usa business_id = 0 en el token
  const tokenBusinessId = isSuperAdmin ? 0 : businessId;
  
  // 1. Intentar obtener token existente (verificar que coincida con el business activo del token)
  let businessToken = TokenStorage.getBusinessToken();
  const activeBusiness = TokenStorage.getActiveBusiness();
  
  if (businessToken && activeBusiness === tokenBusinessId) {
    return businessToken;
  }

  // 2. Obtener session token
  const sessionToken = TokenStorage.getSessionToken();
  if (!sessionToken) throw new Error('No session token available');

  // 3. Super admin siempre genera token con business_id = 0
  // El business_id del contexto se envía como query param en las peticiones
  const result = await generateBusinessTokenAction({
    business_id: tokenBusinessId, // 0 para super admin, businessId para usuarios normales
    session_token: sessionToken,
  });

  if (!result.success || !result.data) {
    throw new Error(result.error || 'No se pudo generar business token');
  }

  // 4. Guardar token para próximas peticiones
  TokenStorage.setBusinessToken(result.data.token);
  TokenStorage.setActiveBusiness(tokenBusinessId);
  return result.data.token;
}, [businessId]);

// Uso en funciones async
const loadData = async () => {
  try {
    const token = await getBusinessToken();
    // El businessId del contexto se pasa siempre (se enviará como query param)
    const result = await someAction({ businessId, token, ...otherParams });
    // ... manejar resultado
  } catch (err) {
    // ... manejar error
  }
};
```

### Arquitectura de Repositorios

Los repositorios **siempre** reciben el token como parámetro y envían el `business_id` como query param:

```typescript
// ✅ Correcto - Token como parámetro, business_id como query param
async getData(params: { businessId: number; token: string; ... }): Promise<Data> {
  const url = `${this.baseUrl}/endpoint`;
  const queryParams = new URLSearchParams();
  queryParams.append('business_id', params.businessId.toString());
  // ... otros query params
  const fullUrl = `${url}?${queryParams.toString()}`;
  
  const response = await fetch(fullUrl, {
    method: 'GET',
    headers: {
      'Authorization': `Bearer ${params.token}`,
      'Content-Type': 'application/json',
    },
  });
}

// ✅ Correcto para POST - business_id también como query param
async createData(params: { businessId: number; token: string; data: CreateDataDTO }): Promise<Data> {
  const url = `${this.baseUrl}/endpoint`;
  const queryParams = new URLSearchParams();
  queryParams.append('business_id', params.businessId.toString());
  const fullUrl = `${url}?${queryParams.toString()}`;
  
  const response = await fetch(fullUrl, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${params.token}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(params.data),
  });
}

// ❌ Incorrecto - NO usar localStorage directamente
async getData(params: { businessId: number; ... }): Promise<Data> {
  const token = localStorage.getItem('token'); // ❌ NO HACER ESTO
}
```

### Server Actions

Las server actions reciben el token y lo pasan al repositorio:

```typescript
'use server';

export async function getDataAction(params: { businessId: number; token: string; ... }): Promise<Data> {
  const repository = new DataRepository();
  const useCase = new GetDataUseCase(repository);
  return await useCase.execute(params);
}
```

### Transformación de Datos

- **Frontend → Backend**: Convertir de camelCase a snake_case
- **Backend → Frontend**: Los datos vienen en snake_case, se mapean a camelCase

### Manejo de Errores

1. **Errores de validación del backend**: Parsear y formatear mensajes en español
2. **Errores HTTP**: Mostrar mensajes claros al usuario
3. **Errores de token**: Redirigir al login si el token es inválido

## Estructura de Módulos

Cada módulo debe seguir esta estructura:

```
module/
├── domain/
│   ├── entities/          # Entidades del dominio
│   ├── ports/             # Interfaces (repositorios, casos de uso)
│   └── index.ts
├── application/
│   └── *.use-case.ts      # Casos de uso
├── infrastructure/
│   ├── repositories/      # Implementación de repositorios
│   └── actions/           # Server actions ('use server')
└── ui/                    # Componentes React
```

## Buenas Prácticas

1. **Server Actions**: Todas las acciones HTTP deben ser server actions
2. **Token Management**: 
   - Siempre obtener el token en componentes client-side y pasarlo como parámetro
   - **Super Admin**: Siempre usa `business_id = 0` en el token (esto NO cambia)
   - **Query Params**: El `business_id` del contexto siempre se envía como query param en las peticiones HTTP (GET y POST)
   - El backend detecta si es super admin y lee el `business_id` del query param si se envía
3. **Error Handling**: Parsear errores del backend y mostrar mensajes en español
4. **Type Safety**: Usar TypeScript estricto, definir tipos para todos los DTOs
5. **Transformación de Datos**: Convertir camelCase ↔ snake_case en los repositorios

## Notas Importantes sobre Super Admin

- **Token**: El super admin **SIEMPRE** usa `business_id = 0` en el token, esto NO cambia
- **Query Params**: Cuando el super admin está trabajando en un negocio específico (ej: `/properties/16/parking`), el `business_id` del contexto (16) se envía como **query param** en las peticiones HTTP
- **Backend**: El backend detecta si es super admin (por `business_id = 0` en el token) y lee el `business_id` del query param si se envía
- **Usuarios Normales**: Los usuarios normales siempre usan el `business_id` del token, el query param también se envía pero el backend usa el del token
